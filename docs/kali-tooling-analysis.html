Extending AI-Detector with Kali Linux tooling

Feasibility + improvement map based on the official Kali Docker images docs and the current engine coverage (apps/web/lib/coverage.ts, app/engine/).

Verdict: yes, feasible — and the codebase already names the exact gaps Kali fills.

coverage.ts LIMITS literally states “nuclei and sqlmap are still not wrapped”, and the NOT_COVERED list plus check caveats enumerate the rest. The repo already has two proven integration templates the Kali tools can slot into: the ZAP sidecar profile (opt-in, profile-gated, HTTP-driven, degrades gracefully) and the WITH_INTERACTSH build-arg (optional tooling baked into the worker image).

1. What the Kali images actually are

Key facts from the official docs

  • kalilinux/kali-rolling is the recommended base; updated ~weekly.
  • Images ship no tools by default — you install via apt.
  • kali-linux-headless metapackage ≈ 2 GB+ of tools — overkill here.
  • kali-last-release = pinned snapshot; bleeding-edge/experimental/dev are for special cases only.

Implication for this project

  • Cherry-pick packages (nuclei, sqlmap, testssl.sh, feroxbuster, seclists) instead of a metapackage — a few hundred MB, not 2 GB.
  • Kali rolling is a moving target; for reproducibility prefer kali-last-release or pin package versions, and rebuild weekly.
  • Honest note: sqlmap and testssl.sh are also in Debian repos, and nuclei/feroxbuster ship as single binaries — so Kali is not strictly required for the top picks. Its value is as a curated toolbox base when you want several tools maintained together in one image.

3. Integration options

Option A — tools in the worker image (cheap wins first)

Extend services/api/Dockerfile with a WITH_KALI_TOOLS-style build-arg, exactly mirroring the existing WITH_INTERACTSH pattern. Invoke tools as subprocesses — the AI planner already shells out to a subprocess, so this is established convention.

  • sqlmap: pure Python, trivial to add; runs only against parameters the engine already flagged → naturally bounded.
  • testssl.sh: in Debian repos; JSON output upgrades the existing TLS check.
  • Best for: phases 1–2 below.

Option B — Kali sidecar service (the real Kali use)

New kali profile service, built FROM kalilinux/kali-rolling with a curated apt set + a thin job API, driven by the worker over HTTP — a structural clone of the ZAP adjunct: profile-gated in compose, kali: true per-run flag, a _run_kali side path in the runner, graceful degradation on any failure.

  • Keeps the worker image lean; heavier tools live in their own container.
  • Matches every existing convention (ZAP_BASE_URL env, make up-zap analogue, *_skipped events).
  • Best for: phases 3–4 below.

Rejected: rebuilding the worker FROM kalilinux/kali-rolling. Rolling-release base under a service with pinned Python deps (python:3.12-slim today) trades reproducibility for nothing — the worker needs a stable runtime, the tools need a toolbox. Keep them separate.

4. Suggested roadmap

  1. sqlmap confirmation pass — highest value per unit effort.

    Subprocess in the worker (Option A). Re-test only parameters already flagged by reflected_injection/signature_injection SQLi leads. Converts heuristic to verified. Opt-in via env/flag like OAST. Bound it: --batch --retries=1 --timeout=5 --delay + wall-clock timeout.

  2. testssl.sh upgrade of the TLS check

    Replaces the single-handshake analysis with full chain / cipher / protocol / OCSP coverage. --json output maps directly to the existing TLS finding shape; stays verified tier.

  3. Kali sidecar + nuclei — the biggest coverage jump.

    New kali compose profile (Option B): nuclei with a curated template subset (CVEs, exposures, misconfigs), -rl rate limit, per-run opt-in, kali_skipped/kali_done events. Add a /coverage group for it, mirroring the ZAP group.

  4. Endpoint discovery (feroxbuster/ffuf) — largest effort, treat as a feature.

    Discovery phase that feeds undocumented paths back as candidate Operations, so existing BOLA/BFLA/injection checks run on shadow endpoints too. Design decision needed: do discovered ops count against the 500-request budget?

5. Guardrails these additions must respect

  • Authorization gate stays. Every Kali-tool pass only fires on an already-authorized run (authorized: true) and only with an explicit opt-in flag, same as ZAP.
  • Outside the 500-request budget — say so. sqlmap/nuclei/feroxbuster make their own requests. Document them as side paths bounded by wall-clock timeout + tool-native rate limits (-rl, --delay), exactly how ZAP is documented today.
  • Graceful degradation is mandatory. Missing tool / container down / timeout → emit *_skipped event, scan completes with engine findings intact. Never fail a scan on an adjunct.
  • Image hygiene. Cherry-picked packages (~hundreds of MB), not kali-linux-headless (~2 GB+). Pin kali-last-release or package versions if scan reproducibility matters.
  • Coverage copy must stay honest. New entries in coverage.ts with correct confidence tier — nuclei template matches are closer to “verified” than reflection, but a template hit is still not exploitation for every class.
